# Dockerized backend and platform-compatibility guide

## Scope and inspected architecture

+one is a managed Expo application (`app/`) and a Node/Express + Socket.IO
backend (`server/`). The inspected versions/configuration are:

| Area | Current implementation |
| --- | --- |
| Mobile/web client | Expo SDK 57.0.13, React Native 0.86.2, React 19.2.3, Metro web bundler |
| Native workflow | Managed Expo; no committed `android/` or `ios/` projects |
| Android floor | `minSdkVersion: 24` (Android 7.0) in `app/app.json` |
| Generated Android toolchain | SDK 36 / build tools 36.0.0, target SDK 36, AGP 8.12.0, Gradle 9.3.1, Kotlin 2.0.21 default (Expo modules), JDK 17 toolchain, New Architecture enabled |
| Builds | EAS profiles in `app/eas.json`; native settings are generated by Expo/EAS during prebuild |
| API/realtime | Express 4 + Socket.IO 4, one long-running Node process on port 4000 |
| Authentication | bcrypt password hashes and JWT bearer tokens |
| Database | `better-sqlite3`; schema migrations run safely at server boot |
| File storage | mounted local disk by default, or Supabase Storage when server-side Supabase credentials are configured |
| Notifications | Expo push plus persisted/generated VAPID keys for browser push |
| Runtime | Node 24, matching the root `.nvmrc` and root `package.json` engine |

Docker is intentionally used **only** for the backend runtime and its
persistent local state. The Docker image also builds the Expo web bundle so the
same backend can serve the web app, but it does not render, emulate, or build
Android/iOS itself. EAS and real device/simulator testing remain required.

There is no separate database container: the actual application database is a
single SQLite file accessed synchronously by this one backend process. Adding
Postgres or Redis just for Compose would invent infrastructure and change the
application's behavior. Socket.IO runs in the backend container as it does in
the existing deployment.

## What Docker provides

```text
Expo Android / iOS / web client
              │ HTTPS or reachable LAN URL in development
              ▼
     Node / Express / Socket.IO container
              │
              ▼
  named Docker volume: SQLite + uploads + backups + VAPID keys
```

- `Dockerfile` is a multi-stage Node 24 build: it creates the Expo web export,
  installs server production dependencies only, starts as root so
  `docker-entrypoint.sh` can chown the `/data` volume (Railway mounts
  volumes as root), then drops to the built-in `node` user. No `.env` or
  credentials are copied into it.
- `compose.yaml` starts only the required backend and its `plusone_data` named
  volume. It uses a read-only root filesystem, `/tmp` tmpfs and
  `no-new-privileges`.
- The server now exposes `GET /health` and keeps `GET /api/health` as a
  backwards-compatible alias. Both return only `{ "ok": true, "time": ... }`
  after SQLite opens and boot migrations complete.
- `JWT_SECRET` is mandatory for `NODE_ENV=production`; Compose fails clearly if
  it is not supplied instead of silently using a development fallback.
- `CORS_ORIGIN` supports a comma-separated allow-list for both HTTP and
  Socket.IO. Use `*` only for local development.

## Local Docker workflow

1. Create a local secret file without committing it:

   ```bash
   cp .env.example .env
   openssl rand -hex 32
   # Put the generated value after JWT_SECRET= in .env
   ```

2. Start the backend and inspect its health:

   ```bash
   docker compose up --build -d
   curl http://localhost:4000/health
   docker compose logs -f backend
   ```

3. Start Expo on the host (not in Docker):

   ```bash
   cd app
   npm ci
   npx expo start
   ```

   Web development on the same machine can reach `http://localhost:4000`.
   An Android emulator normally reaches the host through its emulator-specific
   host alias. A physical device must use a reachable URL, never `localhost`:

   ```dotenv
   # app/.env — local development only
   EXPO_PUBLIC_API_URL=http://YOUR_COMPUTER_LAN_IP:4000
   ```

   For a production EAS build, `EXPO_PUBLIC_API_URL` must be an externally
   reachable **HTTPS** API origin. The app deliberately rejects cleartext
   backend values in release binaries. A LAN tunnel or an HTTPS development
   proxy is therefore the safer route for a physical device when testing a
   custom native development build.

4. Stop containers without deleting state:

   ```bash
   docker compose down
   ```

   Do **not** routinely run `docker compose down -v`; that deletes the named
   volume containing local users, chats, uploads, backups and generated VAPID
   keys. To see the actual volume name, run `docker volume ls` (Compose prefixes
   `plusone_data` with its project name).

`npm run docker:smoke` is a repeatable Docker check. It builds an isolated
Compose project, waits for Docker health, requests `/health` from inside the
container, and shuts down **without** `-v`.

## Configuration and secrets

- Root `.env.example` is for Compose; `server/.env.example` is for a host-run
  backend; `app/.env.example` contains the only Expo public variable.
- Never place `SUPABASE_SERVICE_KEY`, `JWT_SECRET`, VAPID private keys, signing
  files, service-account JSON, or production passwords in an Expo
  `EXPO_PUBLIC_*` variable. Public Expo variables are embedded in the client
  bundle.
- Set `DATA_DIR` only for a host-run backend. Compose fixes it to `/data` and
  mounts that location persistently.
- Optional Supabase/Jamendo/VAPID variables in `.env.example` correspond to
  variables that the backend actually reads. With no Supabase settings, local
  uploads are safely persisted in the Docker volume.

## Database and migration behavior

Schema creation and compatibility migrations are currently code-driven in
`server/src/db.js`. A new or empty named volume follows this sequence on boot:

```text
open SQLite database → enable WAL and foreign keys → create schema → run
idempotent column/index migrations → accept API and Socket.IO traffic
```

This is appropriate for the existing SQLite architecture. Existing production
volumes must be backed up and migrated in place; never reset or remove a
production volume. The backend test suite starts isolated temporary data
folders, providing a fresh-database migration exercise without touching user
content.

## Mobile and browser compatibility checklist

Docker health proves backend reproducibility, **not** universal device support.
Before release, perform the following on the exact EAS build candidate and
record device/OS/browser, API origin and result:

| Target | Required smoke coverage |
| --- | --- |
| Android 7.0 / API 24 practical floor | cold start, sign-in, recovery from bad network, keyboard/navigation, images and low-memory behavior |
| Recent Android + emulator | auth, OTP/reset, Socket.IO reconnect, chat, GC, media upload/crop, stories, Find One, profile and notifications |
| Physical Android device | use reachable LAN/HTTPS API; repeat API and realtime checks off Wi-Fi and after reconnect |
| iOS simulator and physical iPhone when available | sign-in, media permissions, notifications/calls, stories, navigation and Socket.IO |
| Chrome, Edge, Firefox and mobile browser | auth, chat/GC, media, responsive navigation, browser push where permission/platform supports it |
| Slow/offline network | delayed API, timeout UI, retry, upload failure, Socket.IO reconnect and no frozen spinner |

Managed Expo owns Android `compileSdkVersion`, `targetSdkVersion`, Gradle,
Android Gradle Plugin, Kotlin and iOS build settings at EAS prebuild time. They
are intentionally not guessed or manually upgraded in this repository. Before
an EAS production build, run `npx expo-doctor`, validate package compatibility
for SDK 57, then run:

```bash
cd app
npm ci
npx eas build --platform android --profile production
# Run separately when Apple credentials and a simulator/device are available:
npx eas build --platform ios --profile production
```

Use the documented manual matrix above to decide release readiness. Do not say
Docker makes the mobile app compatible with every Android or iOS device.
